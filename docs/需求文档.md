# 即时通讯系统需求文档

## 1. 项目概述

### 1.1 项目名称

IM 即时通讯系统（暂定）

### 1.2 项目目标

构建一个用于学习、演示和求职展示的即时通讯后端项目。项目以单聊和小群聊为核心，重点体现消息可靠性、断线同步、并发控制、服务可观测性等后端工程能力。

### 1.3 目标用户

- 注册用户：能够建立会话、发送和接收消息，并在重新连接后同步离线消息。
- 系统运营/开发者：能够通过日志、指标和管理接口观察服务运行状态并排查异常。

### 1.4 使用的技术

- 语言：Go
- Web 框架：Gin
- 持久化：MySQL，通过 sqlx 访问
- 缓存及跨实例在线路由（计划）：Redis
- 异步消息：Apache RocketMQ，当前用于红包通知
- 实时连接：WebSocket

具体库、部署方式和版本在技术设计文档中确定。

## 2. 功能范围与当前进度

### 2.1 现有能力

- 用户注册、登录和身份认证。
- 通过完整的 `username` 查找用户；支持发送好友申请、同意、拒绝和解除好友。
- 好友可以创建或打开单聊、发送新消息；解除好友后仍可读取已有历史。会话列表和聊天标题显示对方的 `nickname`。
- 创建及管理群聊，支持改名、邀请好友、移除成员、设置管理员、转让群主身份和退出。同群成员可以实时收发文本。
- 通过 HTTP 发送文本和查询历史；MySQL 保存消息及会话序号，重复发送请求返回原消息。
- WebSocket 一次性票据鉴权、心跳、慢连接隔离以及同一账号多端推送。客户端断线重连后可按会话序号补齐消息。
- 会话列表显示最新消息预览和未读消息数。用户在可见页面查看会话最新消息后更新个人已读进度。
- 支持积分余额、流水、单聊和群聊红包、领取及到期退款。文字、图片和红包通知由 Outbox 和 RocketMQ 发布。
- Docker Compose 已配置 Redis 和 RocketMQ；单聊和群聊使用 MySQL 保存消息，通过进程内的 WebSocket 连接推送。

### 2.2 计划能力

- 跨网关实例消息路由、普通消息异步推送、限流和运行指标。

功能范围可以随项目进展调整。第 3 至第 8 节描述目标业务规则和验收条件，当前交付状态以第 2 节为准。

### 2.3 暂不纳入范围

- 真实货币充值、提现、支付渠道和真实资金结算。
- 音视频通话、端到端加密、大规模万人群聊。
- 图片/文件消息、消息全文搜索、复杂内容审核和多地域容灾。

## 3. 核心业务需求

### 3.1 用户与认证

- 用户可以使用账号凭据注册和登录。
- 登录成功后签发有时效的访问凭证；受保护接口和 WebSocket 握手均需鉴权。
- 用户只能读取允许公开的资料字段，不能通过修改请求参数冒用其他用户身份。
- 登录失败、凭证过期和重复注册应返回稳定、可区分的错误码。

### 3.2 好友系统

- 用户通过完整的 `username` 查找对方，并发送好友申请。
- 对方同意申请后，双方同时成为好友。申请待处理或被拒绝时，双方均不能发起单聊或发送新的单聊消息。
- 任一方解除好友后，双方均不能继续发送单聊消息。已有会话和聊天记录保留，双方仍可读取历史。重新成为好友后，继续使用原会话。
- 好友列表、好友单聊会话列表和聊天标题显示在线或离线。只要还有一个设备保持 WebSocket 连接，用户就显示在线。

### 3.3 单聊

- 互为好友的用户可以创建或打开单聊；同一对用户共用一个单聊会话。会话列表和聊天标题显示对方的 `nickname`。
- 读取单聊历史需要会话成员资格；发送单聊消息需要同时满足会话成员资格和好友关系。现有单聊会话同样适用。
- 会话列表按最近活动时间排序，并提供最近消息摘要和未读数。

### 3.4 群聊

- 用户可以创建最多 200 人的群聊，群主和管理员可以邀请自己的好友。重复邀请保留已有成员的角色和已读进度。
- 群主可以改名、设置管理员、移除其他成员和转让群主身份。管理员可以移除普通成员。
- 成员可以主动退出。群主需要转让身份后退出，最后一名成员退出时关闭群聊。
- 同群成员可以互发群内文本消息，无需建立好友关系。会话列表显示群名，聊天消息显示发送者昵称。
- 成员只可查看本次加入后发送的消息。退出或被移除后，会话从列表移除，成员无法读取或发送消息。再次加入时，从新的加入位置开始计算可见消息和未读数。

### 3.5 消息发送与接收

- 单聊和群聊均支持文本消息；文本消息至少包含消息 ID、客户端消息 ID、会话 ID、发送者、会话序号、内容和服务端时间。
- 客户端通过 HTTP 提交消息，服务端持久化成功后返回发送确认；WebSocket 用于向在线接收端推送事件。
- 服务端确认表示消息已持久化，不代表接收端已收到或已读。送达状态和已读状态需分别表达。
- 客户端重试必须复用同一个客户端消息 ID；服务端对同一用户、会话和客户端消息 ID 做幂等处理。同一次群成员关系内的重试返回原消息，重新加入后使用新的客户端消息 ID。
- 同一会话的消息应有可比较的服务端顺序号。消息历史使用游标分页，避免深分页造成性能退化。
- 在线推送可能重复或丢失；客户端按消息 ID 去重，并可按会话游标从服务端补拉。

用户可在「我的」更换头像。新账号和未上传头像的已有账号使用默认图片，上传的头像由 Gin 提供读取。

### 3.6 WebSocket 连接与在线状态

- 登录成功后签发访问凭证。客户端使用访问凭证申请一次性票据，服务端验证票据并建立 WebSocket 连接后，按用户记录有效连接，用于实时推送。
- 同一用户只要仍有一条有效连接，就保持在线。连接断开或心跳超时后清理该连接；最后一条有效连接被清理后，用户进入离线状态。
- 每条连接使用有界发送队列；队列满时关闭该连接，客户端重连后通过消息游标补齐。
- 用户离线期间，服务端照常保存通过权限校验的消息，客户端重连后按会话序号补齐。

### 3.7 离线同步、未读与已读

- 客户端按设备记录已连续处理的最大会话序号，并以此请求增量消息；服务端按序返回后续记录。
- 客户端检测到序号缺口时可以主动补拉。
- 已读状态以用户在会话中的最后已读序号为基准，只能向前更新。未读数按已读序号之后由对方发送的消息计算。
- 在线推送不可作为离线消息的唯一存储或恢复来源。

## 4. 虚拟积分红包需求

### 4.1 业务边界

- 新用户在注册时获得 1,000 积分。迁移为现有用户各发放一次，所有变动均可在「我的 → 积分」查询。
- 红包仅使用系统内虚拟积分，不可充值、提现、兑换现金或对接真实支付。
- 单聊红包遵循单聊发送权限。每个红包只有一份，仅会话对方可以领取。解除好友后，已发出的单聊红包仍可在有效期内领取。
- 群成员可在群内发送和领取红包。群聊红包按等额分配，份数最多为发送时的其他有效成员人数。当前有效成员可以领取本次加入后可见的红包，每人最多一份，发送者不能领取。
- 两类红包都记录每份积分、总份数、剩余份数和截止时间，并保存独立的领取记录。
- 红包有效期为 24 小时。到期后停止领取，将未领取的积分退回发送者。
- 每次成功领取都在会话中新增一条领取消息，领取积分、领取记录、会话序号和通知事件在同一事务中提交。单聊发送者看到「对方领取了你的红包」，领取者看到「你领取了红包」；群聊成员看到领取者昵称。
- 红包全部领完后，聊天卡片显示已领完状态并淡化颜色；历史记录和实时更新采用相同状态。

### 4.2 一致性与安全要求

- 积分以整数最小单位存储，禁止使用浮点数进行金额计算。
- 用户的当前余额保存在 `users.point_balance`，每次变动单独记录在 `point_ledger`。
- 扣减发红包用户余额、创建红包、写入积分流水必须在同一数据库事务中完成。
- 领取操作必须保证红包份数和金额不会超发；同一用户对同一红包最多成功领取一次。
- 余额变更必须有不可变的业务流水；每类业务操作使用唯一业务单号保证幂等。
- 红包创建、领取和退款在同一业务事务中写入 Outbox。后台发布 RocketMQ 事件，消费者通知会话内有权查看红包的在线设备。
- 到期任务由 RocketMQ 延迟投递，退款服务主动拉取。退款仅按红包 ID 查库，事务提交后确认消费；重复执行最多退款一次。
- 对发红包、领取红包等接口实施权限校验、参数校验和必要的频率限制。

### 4.3 异常与边界场景

- 红包不存在、已过期、已领完、用户重复领取、余额不足。
- 同一请求并发重试、多个用户同时争抢最后一个名额。
- 数据库事务失败、MQ 暂时不可用、过期任务重复执行。
- 通过积分账户流水核对红包发出金额、领取金额和过期退款金额。

## 5. 可靠性与异步事件

- 消息持久化与待发布事件使用 Transactional Outbox，避免数据库提交成功但事件永久未发布。
- Outbox 发布器可重试；发布成功后更新事件状态。进程在“MQ 已接收、数据库状态未更新”时异常终止，允许重新发布。
- MQ 消费者必须幂等；不能假设消息只投递一次。
- RocketMQ 用于持久化后的异步分发和业务事件处理，不替代 MySQL 中的消息历史与权威业务状态。
- 当前使用单实例 WebSocket Hub 管理在线状态。关键业务余额、消息历史和幂等记录以 MySQL 为准。
- Redis Pub/Sub 或在线推送不可作为可靠消息存储；客户端通过消息游标补拉弥补推送缺失。

## 6. 数据与接口约束

- 所有时间统一按 UTC 存储，展示层转换为用户时区。
- 主键、消息 ID、会话序号和业务幂等键的生成及唯一性策略在技术设计中明确。
- 列表接口采用游标分页并限制单页数量；请求体、文本长度和频率均需设上限。
- API 使用统一响应格式和错误码；日志不得记录密码、访问令牌等敏感信息。
- 普通 JSON 接口统一使用 HTTP `200`，响应体包含 `code`、`msg` 和 `data`；`code=0` 表示成功，业务错误和服务错误通过响应体区分。WebSocket 握手成功使用 `101`，票据无效使用 `401`，同源校验失败使用 `403`。
- 数据库迁移应版本化，开发和测试环境可重复初始化。
- 数据库使用逻辑外键。查询关联资料时先读取关联 ID，再按 ID 查询对应记录。新增表须附带业务字段说明。

## 7. 非功能需求

### 7.1 安全

- 密码使用成熟密码哈希算法存储，不保存明文密码。
- 对接口、WebSocket 和消息内容执行身份、成员权限及输入校验。
- 配置密钥通过环境变量或外部配置注入，不提交到代码仓库。
- 实施基础限流、连接数限制和敏感操作审计。

### 7.2 可用性与可恢复性

- 数据库事务保证核心写入原子性；异步任务可重试且有幂等保护。
- 服务重启后，持久化消息可查询，未完成的 Outbox 事件可继续投递。
- `/healthz` 检查进程存活，`/readyz` 检查 MySQL 是否可用。RocketMQ 暂停期间可以继续保存消息与处理红包，恢复后补发在线通知。当前部署不提供宿主机故障时的自动切换。

### 7.3 性能与容量验证

- 建立可重复的基准测试，记录硬件配置、实例数、连接数、消息大小和测试时长。
- 至少测量 HTTP 发消息吞吐、端到端推送延迟、WebSocket 并发连接数和数据库查询耗时。
- 简历中的性能数字只能使用实际测试结果，并附带测试条件，不预先承诺未经验证的指标。

### 7.4 可观测性

- 结构化日志包含请求/追踪 ID、用户或会话等必要关联字段，但不泄漏敏感数据。
- 记录关键业务计数、错误率、延迟、活跃连接数、队列积压和重试次数。
- 为 MQ 消费失败、Outbox 积压、WebSocket 异常断开和红包对账差异提供可排查信息。

## 8. 功能验收标准

### 8.1 好友与单聊

- 通过完整的 `username` 找到对方并发送申请；申请待处理或被拒绝时，双方均不能发起单聊或发送新的单聊消息。同意后，双方可以打开同一单聊并实时收发文本，会话列表和聊天标题显示对方的 `nickname`。
- 任一方解除好友后，双方均不能发送新的单聊消息，且仍可查看已有历史。重新成为好友后，可以在原会话继续发消息；已有单聊按相同规则校验。
- 非会话成员无法读取或发送该会话消息。
- 发送请求超时后使用同一个客户端消息 ID 重试时，历史中只产生一条消息且返回结果一致。

### 8.2 群聊

- 群主可以创建群聊、邀请好友、设置管理员和转让群主身份。普通成员无法执行群管理操作，管理员只能移除普通成员。
- 非好友群成员可以实时收发文本，并在断线重连后补拉。会话列表可以看到群名、最新消息预览和未读数。
- 成员退出或被移除后，无法读取或发送群消息。再次加入时，历史、增量同步及会话列表仅显示本次加入后发送的消息。

### 8.3 红包

- 好友单聊的红包只有会话对方可以领取，领取成功后按该份积分入账。未领取时，到期将该份积分退回发送者。
- 群聊红包的每份积分相同，每位群成员最多领取一份。并发领取的成功份数不超过总份数，累计入账不超过总积分；同一成员重复请求不会重复入账。部分领取后到期，只退回未领取的积分。
- 两类红包到期后均无法继续领取，重复执行退款不会重复入账。
- 每次成功领取都会在聊天记录中显示一次领取通知；重复提交领取请求不增加重复通知。
- 红包最后一份领取成功后，发送者和会话成员的红包卡片均更新为已领完状态并淡化显示。

### 8.4 连接与同步

- 仅完成登录时不会建立在线连接；至少一个设备建立有效 WebSocket 连接时记为在线。断开其中一个设备时，其余设备保持在线并继续接收推送；最后一条连接断开或心跳超时后记为离线。
- 接收端断线期间发送的消息，在重连补拉后按会话序号完整呈现。
- 推送重复时客户端可以去重；推送丢失时可通过游标补齐。
- 历史消息支持稳定的游标分页，跨页不重复、不遗漏已提交的消息。
- 自动化测试覆盖认证、权限、幂等、顺序、断线同步和关键故障路径。

## 9. 简历展示原则

- 重点描述亲自实现的机制、边界条件和验证方式，不把计划中的功能写成已完成成果。
- 可展示的工程亮点包括 Transactional Outbox、消息幂等、会话序号、断线补拉、WebSocket 背压、多设备推送和虚拟积分账本。
- 性能数据应注明压测环境、负载和测量口径；不使用脱离条件的并发量或延迟数字。
- 红包模块可展示如何保证并发领取时积分和份数不超发、重复请求不重复入账、到期退款幂等及流水核对。
